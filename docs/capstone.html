Capstone project

Read 200 sources. Answer in one line.

ask·200 is an answer engine in the style of Perplexity, built around two rules: read a lot and say very little. A question goes out to four search engines and seven public APIs at once. Up to 200 result pages are scraped in parallel with Scrapling and cut into passages. The best ten are ranked with BM25, and the answer comes back in 45 words or fewer, with a [n] citation after every claim.

Try the live demo Try it with CLIP·search Read answer.py Read the browser twin

This is the capstone of CLIP VLM 101. The rest of the site ranks images by meaning with CLIP; this project points the same retrieval ideas at the open web, and section 06 joins the two into one system that both sees and reads.

01 · The problem

Search gives you ten links. Chat gives you no sources.

A search engine hands back a list and leaves the reading to you. A chat model reads nothing and answers from memory, so its claims can't be checked. An answer engine sits between the two: it does the reading, and it has to show where each claim came from. The usual weakness is length. Answers grow into paragraphs of hedging that take longer to read than the sources.

The goal: push both ends at once. Read as many pages as one question can justify (200 by default), and keep the answer short enough to read in one glance. If the passages that were read do not support a claim, the engine leaves it out. If none of them answer the question, it says Not in sources.

02 · The design

Six stages, from one question to one cited line

Fan outThe question plus up to 3 rewrites (Claude writes them when a key is available) go to DuckDuckGo, Bing, Wikipedia and Mojeek, and the question to 7 APIs, all at the same time.
ScrapeScrapling's AsyncFetcher fetches up to 200 deduplicated URLs, 40 at a time, with a real Chrome TLS fingerprint.
CleanScrapling XPath keeps paragraphs, lists, headings and code, and drops anything inside nav, header, footer, aside or forms.
ChunkText is split at sentence boundaries into passages of about 80 words.
RankOkapi BM25 keeps the top 10 passages, at most 2 from any one page, so a single source can't take over the answer.
AnswerClaude sees only those numbered passages and must answer in ≤45 words, citing every claim. With no key, the best sentences are quoted verbatim.

The model never browses. It sees only what won the ranking, so every citation points at text the engine actually read.

Two runtimes, one algorithm. Browsers block a page from reading other sites' HTML (CORS), so Scrapling can't run on a static website. The live demo therefore uses the sources that do allow cross-origin reads: Wikipedia (full text of the top articles), Hacker News, Stack Overflow, OpenAlex paper abstracts and GitHub, up to 200 documents. The chunking, ranking, citation and extractive steps are the same code in both languages, and a test checks they agree byte for byte.

03 · Design decisions

What I chose, and what each choice costs

decisionwhytrade-off
BM25, not embeddings, for ranking No model to download, runs in under a second on hundreds of passages, explainable, and simple enough to mirror exactly in JavaScript. Purely lexical: a passage that uses different words for the same idea scores zero.
At most 2 passages per page Forces the answer to draw on several sources instead of one long page. Can drop a third good passage from the single best page.
The model sees passages only Every [n] maps to text that was really scraped, which makes the answer checkable. Bounded by the ranking: if BM25 misses the right passage, so does the answer.
Hard word budget (default 45) Succinctness is enforced in the prompt and adjustable with --words. Nuanced questions get compressed; the sources are one click away.
Extractive fallback Works with no API key and no cost: the best novel sentences, verbatim, with their citations. Quoted sentences don't flow together and can include a near miss.
Claude at low effort, server-side fallbacks A short answer from given passages needs little reasoning, so low effort keeps latency and cost down. Harder synthesis questions may need a higher effort setting.
Bring-your-own key in the browser The site stays static, with no server holding a key. The key stays in the visitor's browser. Visitors without a key see extractive answers only.

05 · Expansion

More of the web: seven APIs, images, an MCP server, and an agent

The fixed pipeline reads one round of search results, as text. Four additions widen what it can reach, let it work with images, and let other tools use it.

piecewhat it adds
sources.py Seven keyless APIs queried in parallel, each returning whole documents rather than links: Wikipedia, Hacker News, Stack Overflow, OpenAlex, arXiv, GitHub and Reddit. Every request still goes through Scrapling, and answer.py now ranks these documents alongside the scraped pages.
multimodal.py Images out: every scraped page gives up its content images (logos, icons and tiny images filtered out), and Wikimedia Commons and Openverse add licensed ones. They are ranked by their alt text, caption and page title, with a boost when their page is cited; --clip re-ranks them by CLIP on the pixels, the same model the rest of this site is built on. Images in: --image photo.jpg turns a photo into a search query, using Claude vision with a key or CLIP tags without one. Images read: when Claude writes the answer it also sees your photo and up to three images from cited sources.
mcp_server.py ask·200 as an MCP server with five tools: ask, web_search, read_page, search_sources and find_images. Any MCP client can call it, for example claude mcp add ask200 -- python3 mcp_server.py in Claude Code. It needs no API key; the calling model writes the final answer from the numbered passages.
research.py Agent mode. Claude runs the search loop itself, deciding what to search next, which page to open and when to stop, using the built-in tools plus any combination of: Anthropic's server-side web_search and web_fetch (--server-tools), remote MCP servers through the MCP connector (--mcp NAME=URL), and local MCP servers over stdio (--mcp-stdio, for example Scrapling's own browser tools with "scrapling mcp"). --image lets Claude see a photo with the question. Every tool call is printed as it happens.

Trade-off: the pipeline is fast and predictable; the agent can follow a lead across several pages but costs more tokens and time per question. The capped word budget and required citations are the same in both.

In the browser: the demo page shows an image strip under each answer, drawn from Wikipedia's article images and five image libraries (Openverse, Commons, the Art Institute of Chicago, the Met and iNaturalist). Ask with a photo by clicking 📷, dropping one on the page or pasting it. With a key, Claude reads the photo; without one, CLIP reads it in the tab. An opt-in setting re-ranks the images with CLIP.

Tested locally: each API parser on responses shaped like that API's format, the MCP server through a real MCP client (listing tools, reading a page, running ask), the agent's tool wiring with a stand-in API client, and a live stdio launch of both this server and scrapling mcp. The image pipeline was tested the same way: a page whose logo, icon and 16-pixel image are dropped while its figure is kept and cited as [1]; CLIP re-ranking with a stand-in encoder; and a photo question where a stand-in Claude received the photo first and a cited page's image. Neither the agent nor vision was run against the live Claude API here, and CLIP was not run on real web images.

06 · One system

CLIP·search ⇄ ask·200: a gallery that sees, an engine that reads

CLIP·search finds images by what they show; ask·200 finds answers by what pages say. Joined, each covers the other's blind spot: CLIP can say a photo is "a cat" but not what breed it is or how to care for it, and a web answer can explain Rayleigh scattering but not find the photo of the sky already in your gallery. The bridge is small on purpose: two shared functions plus links between the pages.

Search → answerEvery text search on the CLIP·search home page also runs ask·200 and shows the web's cited answer above the gallery results. It's keyless, never delays the gallery, and follows the page's web toggle.
Photo → answerSearch by a photo and its nearest gallery images name it (knnTags: their tags, weighted by similarity and tag position). That name becomes a web question. No text model and no key are needed.
Gallery → webEvery gallery photo has an "ask the web ↗" link. ask·200 opens with the photo and reads it from its stored CLIP tags, again without a model or key.
Web → galleryEvery ask·200 question also searches your gallery (BM25 on captions and tags, or CLIP on the pixels), and answer.py --save-images downloads the web's top images with a manifest so ingest.py can add them: answers grow the gallery.

Also exposed as tools: the MCP server's gallery_search and the agent's gallery_search let Claude check your photos and the web in one session.

measured on the committed galleryresult
A photo's vector alone, named by its gallery neighbours 13 of 14 get their own head tag. The castle is outvoted by "tower": its nearest neighbours are the Eiffel Tower and Westminster.
Voting rule Plain similarity voting named only 2 of 14 correctly (the cat came out as "pet", the bear as "wildlife"): shared, generic tags pile up votes. Weighting each tag by 0.5position fixed that, because a tag listed first is the most specific.
Python ↔ browser parity knnTags on all 14 captions and gallerySearch on 4 queries match multimodal.py exactly.
Grow the gallery from answers save_images keeps an image once per pixel hash, skips images smaller than 160 px and dead links, and records URL, page, license and the question.

07 · Limitations

What this does not show yet

  • No answer-quality benchmark. The tests prove the pipeline is correct and consistent, not that its answers are good. The next step is a labeled question set scored for accuracy and citation faithfulness.
  • Search-engine markup can change. The result-link selectors for DuckDuckGo, Bing and Mojeek were written to their known HTML and were not checked against the live sites when this was built. Each engine fails on its own and is reported in the output.
  • Lexical ranking has blind spots. In the benchmark, the extractive answer to "question 42" correctly led with the fact for 42, then used its spare words on a similar but wrong fact. A word budget doesn't guarantee relevance; an LLM answer or a dense re-ranker would filter that.
  • The new APIs were not called live. Their parsers were tested against responses shaped like each API's documented format, not the live services; Reddit in particular may block automated clients.
  • The browser version reads fewer kinds of sites. Only CORS-open APIs, so no news sites, blogs or documentation pages. The command-line version reads any page.
  • Scrape responsibly. Chrome impersonation gets ordinary pages served as a reader would see them; keep --pages modest on sites you don't own and respect their terms.

Next: re-rank BM25's top 50 with a text embedding model (the same two-tower idea the rest of this site teaches), cache scraped pages between questions, and add the labeled evaluation above.

08 · Reproduce

Run it yourself

git clone https://github.com/sugeerth/clip-vlm-101 && cd clip-vlm-101
pip install "scrapling[fetchers]" anthropic

python3 answer.py "why is the sky blue"           # ≤45 words, every claim cited
python3 answer.py "what is OPQ" --words 25 --json # machine-readable, with passages
python3 answer.py --selftest                      # Scrapling crawl of a local fixture
python3 answer.py --bench                         # 200 local pages, timed
node docs/js/test_ask.mjs                         # browser twin matches Python

pip install mcp "anthropic[mcp]"
python3 sources.py "vector quantization"          # all 7 APIs at once
python3 mcp_server.py                             # ask·200 as an MCP server (stdio)
python3 research.py "..." --server-tools --mcp-stdio "scrapling mcp"   # agent mode
python3 answer.py --image photo.jpg "what is this and where?"          # ask with a photo
python3 answer.py "northern lights" --clip                             # rank images by CLIP (needs torch)
python3 answer.py "why do cats purr" --gallery --save-images web_imgs/  # + your gallery, then grow it
python3 ingest.py web_imgs/web_*.jpg                                     # the web's images, now searchable by meaning

Without ANTHROPIC_API_KEY, answers are extractive. Everything above runs on a laptop.
