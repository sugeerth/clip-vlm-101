The story · a blog post

Fourteen images, and the questions they asked.

It started as fourteen pictures and a search box. You type “a cat”, and a small model that has never seen these exact photos ranks them by meaning, in your browser, offline. That demo is honest but tiny — and a tiny honest thing has a way of asking bigger questions. Does it scale? Is it fast? Is it honest when it isn't sure? Can agents run it? Can it reach the whole web — for free? This is what happened when we answered each one, out loud, in code you can read in an afternoon.

00 · the premise

A search box that understands meaning

CLIP maps images and text into one shared space, so “a cat” lands near a photo of a cat without any labels, tags, or training on this gallery. The whole demo is two dot products and a sort. It runs on fourteen committed images with precomputed embeddings, and it works — you can try it right now. But fourteen is a rounding error, and a rounding error is a good place to start asking what a real search would need.

01 · does it scale?

From fourteen to a billion, on the back of an envelope

At fourteen images you scan everything. At a billion you cannot, so retrieval trades a sliver of accuracy for enormous speed — exactly as production vector databases do. We built the whole ladder: ann.py is IVF (scan ~2% of the data, keep ~75% of the truth); hnsw.py is the navigable-small-world graph every modern vector DB defaults to (walk a map, log N hops, more recall per distance computed than IVF); diskann.py is how a billion vectors fit on one 64 GB box — a PQ sketch in RAM, the truth on SSD, only ~L vectors read per query. On top, cascade.py quantizes at every rung (binary → PQ → int8 → exact) and keeps ~all the recall, and scaling.py does the two-billion arithmetic. Every number is measured on synthetic clustered vectors, not asserted.

The lesson: “fast at scale” is a measurement, not an adjective. So we counted every distance computation and every disk read, and printed them.

02 · is it fast — and does the ranking earn its place?

Real-time, and a ranking that never makes you scroll

Search has to feel instant — the grid re-ranks on every keystroke, under 100 ms, and the most relevant images render largest, edge-to-edge with no gaps. But speed isn't the hard part; ranking quality is. Positions one, two and three take about half of all clicks, so a good ranker puts the answer there — and if you have to scroll, it missed. So we built a ranking-quality agent, rankquality.py: it scores the live ranking (precision@3, MRR, nDCG) and adds a scroll penalty from your own behavior. Click the top result and quality stays high; scroll past it and the verdict flips to “ranking missed.” The ranker is graded by the eyes it's trying to satisfy.

03 · is it honest when it isn't sure?

The right to say “I don't know”

A search that always answers will confidently answer wrong. The most valuable thing we added is the ability to abstain. conformal.py gives a calibrated confidence set with a coverage guarantee. judge.py convenes a council of independent rubric-judges, gates each vote, and refuses to rule on a hung jury or without a quorum. debate.py lets those judges actually argue — bounded-confidence dynamics that either converge to consensus or split into named factions. trust.py composes the honesty signals into one verdict, and drift.py watches, on a schedule, whether the live world still matches the one we calibrated for. Every layer can say less rather than bluff.

The lesson: honest disagreement is a result, not a bug — so we surface the dissent instead of averaging it away.

04 · can agents run it?

A supervisor that spends compute only on doubt

The pipeline used to be static — every query paid for every stage. So we made it agentic the way the 2025–2026 production systems are. orchestrate.py is an escalation ladder: a cheap glance handles the easy cases, escalates to the full panel only when uncertain, and to a debate only when the panel splits — resolving most cases in one call instead of three. And flow.py is the general form: a typed graph of agents where every hand-off is a schema-checked contract, so a sub-agent that goes off-spec is quarantined and the graph fails closed. You can watch a case flow through it, live, node by node.

05 · can it reach the whole web — free?

You don't crawl the internet. Someone already did.

The gallery is small because we didn't index more — but the internet's images are already indexed, free, at billion scale, in this very CLIP space. LAION crawled ~5.5 billion image-text pairs from Common Crawl and released them CLIP-embedded (the safety-cleaned Re-LAION-5B); clip-retrieval serves nearest-neighbour search over them. So searching the web isn't a crawl you run — it's a query you send, and the index cost is zero, because someone already paid it and gave it away. web.py is the client, in the same record shape as the local gallery, so the same grid and ranking-quality agent work over fourteen images or five billion.

06 · the method

Why you can trust any of this

None of it is a slide. Every capability ships as a Python module and a byte-identical JavaScript twin — the same math in two languages, pinned against each other so the browser never drifts from the reference. Everything runs model-free on the committed data, so the tests need no downloads and no GPU. Each module was adversarially reviewed before shipping — a skeptic agent whose only job was to break it — and real bugs were caught and fixed in the open (a graph that failed open on a prototype-poisoned key; a twin that diverged on empty input; an index that dropped a node from its own layer). And CI re-runs all of it on every push: the Python suite, sixteen JS twins, and every model-free demo.

That's the whole trick. Not one big clever thing, but many small honest ones — each measured, each testable, each readable — stacked until fourteen images became a fast, honest, agentic, internet-scale search you can hold in your head.
